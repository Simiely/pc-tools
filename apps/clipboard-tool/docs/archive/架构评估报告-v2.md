## 一、本轮调研依据（v2 新增对照基准）

| 来源 | 核心标准 |
|---|---|
| **有限状态机 FSM**（dev.to / greatstate / tsight.io） | UI 状态应显式建模（Idle/Loading/Success/Error），事件→状态迁移唯一确定；**布尔标志 ≥4 个时交互矩阵失控，应转状态机**；多步骤异步流程必须状态化 |
| **模块化五原则**（php.cn / dev.to） | 单一职责（函数>20 行/多 if-else 即拆分信号）、显式依赖、稳定接口、避免 mega-file（2000+ 行红线）、依赖方向内聚（UI→Logic→Domain→Infra） |
| **Vanilla JS 分层**（skillsmp.com / copyprogramming） | Core(纯逻辑) / UI(渲染) / App(编排) / Data(持久化) 四层，依赖只向下；无框架项目同样适用 |

## 二、主线逻辑评估 —— 清晰 ✅（评级：A，较 v1 提升）

**主线 = 复制内容 → 自动弹出 → 存入/去重**。

### v0.4.2 重构后的触发链（对照 FSM 标准）

```
clipboardchange 事件
   ├─ 未登录 → return（守卫 1）
   ├─ 来源抑制（卡片复制窗口期）→ return（守卫 2）
   ├─ 已有弹窗 → return（守卫 3）
   ├─ 读剪贴板 → 比对仓库
   │    ├─ 重复 → 直接开编辑页(带"已有相同内容"标记)  ← 单窗口直达
   │    └─ 不重复 → openPasteModal(true) 自动填入       ← 单窗口直达
```

**对照 FSM 标准**：触发决策从"先弹窗再比对（弹错窗口再换）"重构为"**先比对再决定弹什么**"——状态迁移唯一确定，不再有中间态闪烁。这是本轮最重要的架构修正，符合"显式状态转换"原则。

**主线 5 步走查**：复制 → 守卫判断 → 比对 → 单窗口直达 → 存入/编辑，无断层。评级 **A**。

## 三、支线逻辑评估 —— 清晰 ✅（评级：A-，较 v1 持平）

| 支线 | 状态 | 说明 |
|---|---|---|
| 登录限流 | ✅ | ip:userId 维度（v0.3.1 修连坐） |
| 会话失效 | ✅ | 401 → resetFilter 完整重置 → 回选用户页 |
| 过期清扫/会话清理 | ✅ | 独立后台任务，60s 周期 |
| WebDAV 墓碑裁决 | ✅ | mergeSnapshots 单一函数，边界单测通过 |
| 图片 hover 预览 | ⚠️ | **本次评估重点：功能完整但状态管理偏"手工"** |

**扣分点（A- 原因）**：

1. **hover 预览缩放状态用手工布尔/变量**（`scale` + `hoverTimer` + `hoverBox` + `dragging` 状态分散在闭包里，无显式状态机）。当前规模（<50 行）可控，但若继续加交互（双击重置、快捷键）会踩 FSM 警告的"布尔失控"红线
2. `clipboardchange` 守卫链是隐式状态机（靠注释 + 顺序表达），无显式状态枚举——**可读性好但不可测试**（无法对"重复/不重复/有弹窗/来源抑制"四分支做单测）
3. 个别 `catch {}` 静默（容错但丢可观测性）

## 五、结论汇总

| 维度 | v1 评级 | v2 评级 | 变化 |
|---|---|---|---|
| 主线逻辑 | A | **A** ✅ | 触发链重构后单窗口直达，无中间态闪烁 |
| 支线逻辑 | A- | **A-** ✅ | 持平；hover 预览状态偏手工是隐患 |
| 模块化 | B+ | **B+** ⚠️ | 前端弹窗函数化/入口拆分收益显著，但 app.js 单文件 1353 行 + openDataModal 偏大 |

**核心判断**：v0.4.2 重构（先比对再弹窗）解决了主线最大的"逻辑没理顺"问题，主线达到状态机级别的确定性；前端从"单文件全堆"走向"弹窗函数化 + 职责拆分"，模块化方向正确。

**建议的下一步（按性价比）**：
1. **hover 预览状态显式化**：`scale/hoverTimer/hoverBox/dragging` 收敛为单一状态对象（如 `{open, scale, step}`），或至少把 zoom 逻辑抽独立函数——防"布尔失控"
2. **openDataModal 拆 WebDAV 配置**：156 行 → WebDAV 区独立函数，其余保持
3. **app.js 二次拆分**：>1000 行后建议按"弹窗层/渲染层/工具层"拆 2-3 个文件（若继续加功能）
4. **clipboardchange 四分支可测性**：把"读剪贴板→比对→决策"抽成纯函数（输入剪贴板文本+clips，输出 'dup'|'new'|'none'），可单测

> 结论均以调研标准为基准对照得出。当前版本**主线 A / 支线 A- / 模块化 B+**——作为中小型工具已属良好水平；若继续迭代，建议先做 #1（状态显式化）和 #2（弹窗拆分）。
