# clipboard-tool 架构评估报告（基于调研对照）

> 评估日期：2026-08-12
> 评估方法：**调研驱动**——先检索主流架构标准（Node.js 项目结构最佳实践、单文件前端应用评估框架），再逐行对照代码给出结论，非主观臆断
> 评估对象：server.mjs + lib/core(6) + lib/routes(6) + public/index.html + scripts(7)

---

## 一、调研依据（结论的对照基准）

| 来源 | 核心标准 |
|---|---|
| Node.js 官方社区最佳实践（dev.to / bizarro / justinmalinow 2025） | 分层：config / modules(按业务) / middleware / utils / entry；**routes 不含业务逻辑**；组件按业务域划分而非技术角色；单一职责、显式依赖、接口稳定 |
| 单文件前端评估框架（htmlfile.cloud / deepwiki / fyre.site） | 单文件适合 ≤200 行小型工具；超过后必须用「注释分区 + 小函数 + 统一顺序」维持可维护；**甜蜜点 = 小型工具页** |
| 中文社区实践（CSDN 分层架构 / 组件五原则） | 按业务域组织、组件间只通过公共 API 通信、自治性、可替换性 |

---

## 二、主线逻辑评估 —— 清晰 ✅（评级：A）

**主线 = 用户从进入到使用的完整流程**：选用户 → 进入 → 存入 → 管理 → 备份。

| 环节 | 代码位置 | 判断 |
|---|---|---|
| 用户选择页 → 进入 | `renderUserSelect` → `enterUser` → `/api/session` | ✅ 单一入口，无分支散落 |
| 万能存入 | `openPasteModal` → `/api/clips`（自动识别 URL/文本/文件） | ✅ 一条主路径 |
| 列表展示 | `renderMain` → `renderList` → `clipCard` | ✅ 渲染管线清晰 |
| 编辑/删除/星标 | `openEditModal` / `askConfirm` → 对应 API | ✅ 各操作独立小函数 |
| 数据备份 | 设置弹窗 → WebDAV / 导出导入 | ✅ 集中在设置区 |

**主线证据**：`render()` 是唯一视图切换枢纽（127 行），`api()` 是唯一请求封装（137 行），`guard()` 统一防连点。**主线 5 步走查无跳转断层**——从用户选择到存入的代码路径可以在 3 个函数内追完。

---

## 三、支线逻辑评估 —— 清晰 ✅（评级：A-）

**支线 = 异常处理、边界条件、后台任务、安全**。

| 支线 | 位置 | 判断 |
|---|---|---|
| 会话失效 | `handleSessionLost`（177 行） | ✅ 401 统一回选用户页 |
| 登录限流 | `isLoginBlocked/noteLoginFail` | ✅ 独立模块（v0.3.1 已修连坐） |
| 过期清扫 | `sweepExpired`（60s 周期） | ✅ 独立后台任务 |
| 会话清理 | `pruneExpiredSessions`（60s 周期） | ✅ 独立后台任务 |
| WebDAV 墓碑 | `mergeSnapshots` 单一裁决函数 | ✅ 边界单测通过（相等/新于/晚于） |
| 滚动归档 | `rollToArchive` 单一函数 | ✅ 收敛在一处 |
| 错误响应 | `httpError` + 路由 `sendJson` | ✅ 统一 `{ok:false,error}` |

**扣分点（A- 原因）**：
1. `loginGuard`/`sessions` 等内存表与 `users.json` 落盘逻辑混在 users.js 一个文件里——会话域和用户域耦合（221 行内两个域）
2. 前端 `index.html` 1251 行——**远超单文件甜蜜点（200 行）**，但用注释分区（"---------- 用户选择页 ----------" 等）部分弥补
3. 支线错误处理有少数 `catch {}` 静默吞错（如 clipboardchange 监听）——符合"容错"但丢失可观测性

---

## 四、模块化评估 —— 良好，但有明确改进空间（评级：B+）

**对照"组件五原则"逐项打分**：

| 原则 | 现状 | 得分 |
|---|---|---|
| **单一职责** | ✅ core 层 6 文件各管一域：clips/users/files/webdav/config/store | 9/10 |
| **分层清晰** | ✅ core(业务) ← routes(HTTP) ← server(入口)，**routes 不含业务逻辑** | 9/10 |
| **显式依赖** | ✅ 模块间通过 import 显式依赖，无隐式全局 | 8/10 |
| **接口稳定** | ⚠️ 无版本化；`importClips` 等导出直接暴露内部 | 6/10 |
| **可替换性** | ⚠️ store.js 是唯一边界（数据访问），但 webdav 直接操作 fs 绕过 store | 6/10 |
| **按业务域组织** | ✅ 比"按技术角色(routes/controllers/models)"更优 | 9/10 |

**符合调研标准的优点**：
- `lib/core/` 是纯业务层（不碰 HTTP），`lib/routes/` 是纯 HTTP 层（不含业务）——**完全符合"routes shouldn't contain business logic"**
- 配置集中 `config.js`（67 行，全部常量）
- 后台任务独立（sweepExpired / pruneExpiredSessions / runAutoSync）
- 测试脚本独立 `scripts/`（smoke-test 34 用例）

**差距点（对照调研）**：
1. **前端 1251 行单文件**是最大模块化短板——调研建议的"hybrid 过渡态"（JS 抽到独立文件）未做
2. **users.js 混合两个域**：会话(sessions) + 用户(users) 同一文件，建议拆 `sessions.js`
3. **webdav.js 直接操作 fs**（299 行）绕过 store 层，数据访问未统一收口
4. **无类型/无 lint**：JS 原生，靠 `node --check` 兜底语法
5. `scripts/refactor-entry.mjs`、`inline-py.mjs` 等一次性脚本留在仓库（可归档）

## 五、结论汇总

| 维度 | 评级 | 一句话 |
|---|---|---|
| 主线逻辑 | **A** ✅ | 用户流程单一枢纽，5 步走查无断层 |
| 支线逻辑 | **A-** ✅ | 异常/后台/安全各自独立，偶有静默吞错 |
| 模块化 | **B+** ⚠️ | 后端分层符合最佳实践；前端单文件是短板 |

**核心判断**：作为一个**单用户/小团队的中小型工具**，后端 `core/routes` 分层的模块化程度**高于同类项目平均水平**（调研里大量教程项目 routes 里堆业务逻辑，本项目没有）；主要矛盾集中在前端 1251 行单文件——目前靠注释分区勉强可维护，但**继续加功能会撞墙**。

**建议的下一步（按性价比排序）**：
1. **前端 JS 拆分**（`public/app.js` + 注释分区保留）——最大收益，解决 1251 行问题
2. **users.js 拆 sessions.js**——后端小重构，10 分钟
3. 数据访问收口到 store.js（webdav 改走 store）——提升可替换性
4. 补 `node --check` 到 CI/脚本——低成本质量门

> 说明：以上结论均以调研标准为基准对照得出，非拍脑袋。是否执行拆分，取决于"还要不要加功能"——如果到此为止，现状完全够用；如果继续迭代，建议先做 #1 #2。
