## 详细问题描述与复现

### 🔴 问题 1：新存入条目被滚动归档立即移走（最严重）

**位置**：`lib/core/clips.js` → `rollToArchive()`

**现象**：用户已有 500 条以上条目（尤其带复制次数的），再存新条目 → 新条目（copyCount=0）排到排序末尾 → 被滚进归档 → **刚存的条目列表里看不到**，只有勾选"含归档"才找得到。

**复现**（实测）：
```
构造 505 条 copyCount>0 的条目 → 新存 1 条 copyCount=0
活跃区: 500 / 归档区: 6
活跃区含新条目: false | 归档含新条目: true   ← 新条目被归档了！
列表条数: 500（新条目不在其中）
```

**根因**：`rollToArchive` 用 `sortClips()`（置顶 → 复制次数 → 更新时间）保留前 N。新条目的 copyCount=0 会排在有复制次数的旧条目后面，被当成"低价值"滚走。

**影响**：任何存满 500+ 条的用户，每次存入新内容后立即消失，体验极差。

**建议修复**：滚动判定改为「保留最近更新的 N 条」或「保留最近 created 的 N 条」，复制次数只作次级排序；或 rollToArchive 时优先排除刚创建的（如 updatedAt 在本次会话内的）。推荐按 `updatedAt` 倒序保留（最近用过的留下），而不是按 copyCount。

### 🔴 问题 2：登录限流全局连坐

**位置**：`lib/core/users.js` → `loginGuard` + `lib/routes/users.js` 登录路由

**现象**：限流按 `req.socket.remoteAddress`（IP）记。本机所有请求都是 `127.0.0.1`，**用户 A 输错 8 次密码 → 用户 B、C 全部被锁 60 秒**。

**复现**（实测）：
```
用户 A 连续输错 8 次 → A 用正确密码登录 → 429 "尝试过于频繁"
用户 B（无密码）登录 → 429（被 A 连坐）
```

**根因**：`LOGIN_MAX_FAIL=8` + `LOGIN_WINDOW_MS=60s` 按 IP 维度。

**影响**：多用户工具里一个手滑输错密码的用户会锁住所有人（尤其本地/内网部署时所有请求同一 IP）。

**建议修复**：限流 key 改为 `ip + ":" + userId`（或至少 `ip + 目标用户`），只锁「同一 IP 对同一用户」的暴力尝试；用户不存在时用 IP 单独限流。

### 🔴 问题 3：会话失效后列表空白

**位置**：`public/index.html` → `handleSessionLost()`（177 行）

**现象**：会话失效（401）→ `handleSessionLost` 执行 `state.filter = { q: "", tag: "" }` → **缺 `type` 和 `archived` 字段**。重新进入用户后 `renderList()` 里 `state.filter.type` 为 undefined → `if (ty !== "all")` 为 true → `c.type === undefined` 永远 false → **全部条目被过滤，列表空白**。

**代码确认**：
```js
// 177 行：缺 type / archived
state.filter = { q: "", tag: "" };
// 而 resetFilter() 是完整的：
function resetFilter() { state.filter.q = ""; state.filter.tag = ""; state.filter.type = "all"; state.filter.archived = false; }
```

**触发路径**：被删号 / 服务重启（token 失效前的旧 token）/ 被踢 → api() 捕获 401 → handleSessionLost → 再进入任意用户 → 空白。

**建议修复**：`handleSessionLost` 改为调用 `resetFilter()`，或直接 `state.filter = { q:"", tag:"", type:"all", archived:false }`。

### 🟡 问题 4：删除用户后配置文件残留

**位置**：`lib/core/users.js` → `deleteUser()`

**现象**：删除用户只清理了 `<uid>.json`、`<uid>.archive.json`、`files/<uid>/`，**没有删除 `<uid>.tombstones.json`（墓碑）和 `<uid>.webdav.json`（WebDAV 配置）**。

**复现**（实测）：建用户 → 删条目（产生墓碑）→ 删用户 → `users/` 目录残留 `<uid>.tombstones.json`。

**影响**：残留文件长期累积（墓碑文件可能含 id 列表、webdav 配置含密码明文——**安全风险**：密码残留在磁盘）。

**建议修复**：deleteUser 里补充：
```js
rmForce(path.join(CONFIG.usersDir, uid + ".tombstones.json"));
rmForce(path.join(CONFIG.usersDir, uid + ".webdav.json"));
```

### 🟡 问题 5：标签重命名为空值 → 静默删除

**位置**：`lib/core/clips.js` → `renameTag()`

**现象**：`PUT /api/tags/xxx {"name":"  "}` → 未报 400，而是把所有条目的该标签替换成空串并被 `filter(Boolean)` 剔除 → **等价于删除标签**。

**复现**（实测）：
```
PUT /api/tags/目标标签 {"name":"  "} → { ok:true, affected:1 }
GET /api/clips → 条目标签: []   ← 标签被删了
```

**根因**：校验只查 `!from || from === to`，没查 `!to`（空目标）。

**建议修复**：加 `if (!to) throw httpError(400, "标签名无效")`。

---

### 🟢 问题 6：链接自动标题带追踪参数

**位置**：`lib/core/clips.js` → `createClip()` link 分支

**现象**：URL 被 `cleanUrl` 清理了，但自动标题用的是**原始 url**。

**复现**（实测）：
```
存链接 https://ex.com/p?utm_source=x（不填标题）
→ title: "https://ex.com/p?utm_source=x"  ← utm 残留
→ url: "https://ex.com/p"                 ← 已清理
```

**建议修复**：`clip.title = clip.url.slice(0, 60)`（用清理后的）。

---

### 🟢 问题 7：归档不进 WebDAV 快照（文档缺失）

**位置**：`lib/core/webdav.js` → `runSync()`

**说明**：同步快照只含活跃区 `loadClips()`，归档是本地扩展——设计合理（避免把大量归档数据同步到远端），但 README 未说明，用户勾选"含归档"看到的条目**不会**被备份。建议在 README/设置弹窗标注「归档不参与 WebDAV 同步」。
