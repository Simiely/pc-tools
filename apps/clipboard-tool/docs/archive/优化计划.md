## 〇、检索与验证记录（2026-08-14 第二轮补做）

### R1. mock-webdav 路径 bug 根因 —— 🟢 本地实验实锤

`node -e` 实测：`path.join("/tmp/mock-webdav", "dav/probe")` 产出 `\tmp\mock-webdav\dav\probe`（**无盘符**），而 `path.resolve("/tmp/mock-webdav")` 产出 `D:\tmp\mock-webdav`（**有盘符**）→ `startsWith` 恒 false → 400 bad path。用 `C:/Temp/...` 绝对路径两侧一致 → 正常。
**修复方案已验证**：safeJoin 改为 `path.resolve(path.join(DATA, rel))` 或 `path.resolve(DATA, rel)` 均可行，且能正确拦截 `../` 逃逸（实验 C：`D:\tmp\outside` startsWith=false ✅）。

### R2. safe-delete 坑 —— 🟢 实测 + 🔵 权威来源，**文档表述需要修正**

- 本机 `NODE_OPTIONS` 含 `--require=".../genie-safe-delete.cjs" --use-system-ca`，`fs.rmSync.name === "wrappedRmSync"`——**是 WorkBuddy 环境注入的 shim**，把 fs.rmSync 猴补丁为"送回收站"（genie-trash 二进制在 Win11 无交互上下文返回 exit 1 + "Some operations were aborted"，但文件实际已删除）。
- 多位置实测：`C:\Users\wandou\` 和 `D:\workbuddy\...\clipboard-tool\` 下 rmSync **抛 [safe-delete] 错但实际已删**；`C:\Temp\` 下正常。→ 触发位置与回收站/受保护目录相关，**非全局**。
- **结论**：AGENTS.md / DEVELOPMENT.md 写的"Node 22 Windows 上 fs.rmSync 的 safe-delete 机制"表述**不准确**——根源是 WorkBuddy shim 注入（AI 沙箱环境特有），用户手动 `node xxx.js` 时 NODE_OPTIONS 为空、rmSync 原生正常（搜索结果确认此差异）。**rmForce 的容错设计依然正确**（AI 环境内确实抛错），但文档应改为"WorkBuddy 环境注入的 safe-delete shim"而非"Node 22 原生机制"。
- 行动变更：P0-4 文档纠偏增加此项（AGENTS/DEVELOPMENT 关键坑重写）。

### R3. 无 package.json 时 .js 的模块类型 —— 🟢 实测 + 🔵 官方文档

- 实测：无 package.json 时 `import('./lib/core/clips.js')` 成功（ESM 语法探测生效）。
- 官方（nodejs.org ESM 文档 + v22.7.0 release notes）：**module syntax detection 自 Node 22.7 默认启用**；对无 type 字段的 .js 文件先按 CJS 解析，失败则按 ESM 重试；官方建议"add 'type':'module' to eliminate the performance cost"（有轻微性能开销）。
- 结论：C-4 判断成立但需细化——不是"隐患"，是"靠语法探测、有微性能开销"。**P0-1 补 package.json 有官方依据**（消除探测开销 + 显式声明，与 Node 版本/工具链行为解耦）。

仓库 9 commits、main 分支、最新 2026-08-13（v0.5.0-设计稿）；**无 open issues/PR、无 releases、无 .github/workflows**（CI 为空——P1-5 成立）。
